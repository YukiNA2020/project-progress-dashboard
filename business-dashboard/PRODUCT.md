# PRODUCT.md · 业务项目看板

## 一句话

把脑子里散落的海外项目进展，变成一张能一眼看懂的看板：**每个项目卡在哪、下一步找谁、什么时候要交**。

## 为什么做这个

使用者是家电厂海外业务的管培生，手上同时跟 5～6 个海外项目，信息来自微信群聊、邮件、电话、当面沟通，散在四五个地方。真实痛点不是"没有数据"，而是：

1. **状态记不住** —— 被领导问"XX 项目到哪一步了"，要现场翻聊天记录。
2. **卡点说不清** —— 知道"有问题"，但说不出卡在谁、卡了几天。
3. **下一步漏掉** —— 答应的动作没落到具体日期，过了才发现。
4. **数字不可信** —— 口头说的交期和系统里的交期不是一个，自己也不确定哪个算数。

## 目标用户与场景

**唯一用户**（当前阶段）：本人，一台电脑，单机使用。

主要场景：

| 场景 | 频率 | 要解决的事 |
|---|---|---|
| **项目盘点** | 每周 / 接手新项目时 | 一次把手上所有项目的现状过一遍，形成完整底账 |
| 会后补录 | 每天 | 刚开完会/打完电话，趁记忆热把进展录进去 |
| 被问进度 | 随时 | 3 秒内答出"这个项目现在什么阶段、卡在哪、下一步谁做什么" |
| 周报素材 | 每周 | 导出本周变化，直接拼进周报 |

## 设计原则

1. **录入要快过不录。** 任何一次录入如果超过 40 秒，就会变成"回头再补"，然后永久丢失。所以优先保证"最少点击"。
2. **不确定就标出来，不要替用户猜。** 字段猜错比字段空着更糟——空着用户知道要填，猜错了用户会信。所有自动抽取的字段必须带置信度和原文出处。
3. **原文是第一手证据。** 每条项目状态的背后必须能追到"什么时候、谁说的、原话是什么"。这是这类工具唯一能建立信任的方式。
4. **数据不出本机。** 客户名称、项目名、交期属于公司敏感信息，任何联网方案默认关闭。
5. **视觉不动。** 现有前端形态是用户确认过的，后端改造不得改变布局与交互。

## 明确不做（当前阶段）

| 不做 | 原因 |
|---|---|
| 多用户 / 账号 / 权限 | 只有一个人用，做了纯浪费 |
| 云端同步 | 客户数据出不了内网，这是红线不是偏好 |
| 移动端 App | 手机上用网页版足够 |
| 甘特图 / 资源排期 | 项目只有 5～6 个，月历视图够用 |
| 自动从邮件/微信抓取 | 需要读客户端数据库，合规与实现成本都不划算 |
| 财务 / 成本核算 | 不属于当前轮岗岗位职责，且是最高敏感数据 |

## 成功标准

明天带公司用完，如果满足以下三条就算成立：

- [ ] 6 个项目的阶段、卡点、下一步、关键日期全部录入，且没有一条是错的
- [ ] 被问任意一个项目的状态，能在 10 秒内答出来（不用翻记录）
- [ ] 关掉浏览器再打开，数据还在

一周后仍然每天打开，才算真正有用。

## 术语表

| 术语 | 含义 |
|---|---|
| 阶段 | 型号所处的业务环节：报价 → 立项 → 开发 → HR过号 → 滚动计划 → 生产 → 抽检 → 发运 → 在售，可自定义 |
| 关键时间点 / 里程碑 | 有明确日期的事件，如「报价 DDL」「出货日」 |
| 卡点 | 当前阻碍项目推进的具体问题 |
| 下一步动作 | 下一个具体要做的动作，含责任人和时间 |
| 待确认字段 | 系统自动抽取但把握不足，需要人工复核的字段 |
| 复盘录入 | 用自然语言描述进展，由系统抽取成结构化字段 |
