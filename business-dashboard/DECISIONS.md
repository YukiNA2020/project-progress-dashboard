# DECISIONS.md · 关键决策记录

格式：每条记录 **背景 → 选择 → 否掉的方案 → 代价 → 什么情况下该重新考虑**。

---

## D1 · 前端做双模式（后端 + 离线），而不是纯后端

**背景**：明天要在公司配的 Windows 电脑上使用。那台机器不一定有 Python，我也不确定用户有没有安装软件的管理员权限。这个风险无法在今晚预先验证。

**选择**：`index.html` 启动时探测 `/api/health`，探测到就用后端，探测不到就静默降级到 localStorage。两种模式共用同一套数据结构与渲染代码。

**否掉的方案**：
- 纯后端：环境不对就完全不能用，明天白跑一趟。
- 打包成 Windows exe：我在 macOS 上打不出 Windows 可执行文件；且 PyInstaller 产物体积大、杀软易误报。
- 放弃后端，只用 localStorage：数据随时可能因清缓存丢失，作为"重要工作记录"不可接受。

**代价**：数据层要维护两套实现；两套解析算法要保持一致，否则同样一句话在两种模式下抽出的字段不同（这是最容易出的坑，已写进 `AGENTS.md` §9）。

**何时重新考虑**：确认公司电脑有 Python 且能装包之后，可以砍掉离线模式的写路径（保留只读降级）。但只要还有"换机器"场景，双模式就仍有价值。

## D2 · API 输出形状贴合现有前端，而不是规范化设计

**背景**：前端已有约 750 行渲染代码，直接消费 `DB.projects[]` 这个形状，其中 `phase` 是**阶段名称字符串**、`done` 是**名称数组**。数据库里正确的做法是用外键 id。

**选择**：数据库内部规范化（`phase_id` 外键、`done_phases` 独立表、`milestones` 独立表），但 API 出口做一层 `to_client()` 适配，输出与前端现有 JSON **字段完全一致**的形状。

**否掉的方案**：把前端改成消费规范化模型。更"正确"，但要重写全部渲染逻辑，今晚做不完，且必然引入新 bug。

**代价**：多一层适配代码；`done` 用名称而非 id，阶段改名时要级联清理（已在前端 `savePhases()` 有先例，后端照抄）。

**何时重新考虑**：项目数超过 200 或需要多端复用时，值得做一次彻底的规范化重构。当前 5～6 个项目，不值得。

## D3 · 默认不接 LLM，解析先用本地规则引擎

**背景**：这是本次最重要的判断。现有 `demoParse()` 是假 AI，用户自然期待"接个大模型"。但：

- 用户所在公司明令外部 AI 不能接触内部数据；客户名称、项目名称、交期属于敏感信息；
- 明天的真实任务是"把 6 个项目的状态理清楚"，这在录入时是**结构化填空**，不是开放式理解，规则引擎足够；
- 会议原话里 80% 的信息是 "11/10 到 12/5"、"下一步催老李"、"卡在模具" 这类高度模式化的表达。

**选择**：本地规则引擎为主，`app/providers/` 只留接口与契约，`llm.py` 在 P2 之前不实现。UI 不出现"AI 解析"字样。

**否掉的方案**：直接调 OpenAI/DeepSeek。抽得准、写起来快，但**第一句话输进去就把客户名单发出去了**，这是红线不是偏好。

**代价**：解析准确率不如 LLM，遇到复杂长句会抽不全。缓解方式是"不确定就标待确认 + 允许手改"，而不是硬猜。

**何时重新考虑**：满足三个前提才做——(1) 有脱敏方案（客户名 → 代号映射，本地还原）；(2) 用户能接受逐次确认外发；(3) 失败可降级。三条缺一不做。

---

## D4 · 用 FastAPI，而不是纯标准库

**背景**：原版项目 `project-progress-dashboard` 用的是 FastAPI，已在同机验证可跑；本机 anaconda 已自带 fastapi/uvicorn/pydantic。

**选择**：复用 FastAPI。依赖只有 3 个，且都是纯 Python 包（Windows 上 `pip install` 不需要编译器）。

**否掉的方案**：
- 纯 `http.server`：零依赖最安全，但路由、JSON 解析、请求校验、错误处理全要手写，代码量翻倍且易出低级 bug，今晚时间不够。
- Flask：同样要装，功能比 FastAPI 少（无自动校验、无 OpenAPI）。

**代价**：Windows 上需要 `pip install`。若失败，离线模式保底。

**何时重新考虑**：若确认目标机器无 pip 权限，可评估用 `sqlite3 + http.server` 重写（约 300 行），但那是应急方案不是首选。

## D5 · SQLite 单文件，而不是 JSON 文件

**背景**：数据量极小（< 200 KB），看似 JSON 文件更简单。

**选择**：SQLite。

**理由**：JSON 全量读改写有三个致命问题——(1) 写到一半崩溃会损坏整个库；(2) 无法做事务，一次业务操作跨多表时必然出现中间态；(3) 每次保存要序列化全量，随数据增长而变慢。SQLite 一个文件解决全部，且能直接用 DB Browser 查看、能整文件拷走备份。

**代价**：多一层 SQL。但表只有 8 张，都是简单查询。

**何时重新考虑**：不需要。这个规模一直用 SQLite 就对了。

---

## D6 · 不做鉴权

**背景**：安全上"必须有鉴权"是常识，但这里的情况是：单用户、数据在本机、服务只绑 `127.0.0.1`。

**选择**：不做账号密码，只做两层防护：绑定回环地址 + Host/Origin 守卫（防恶意网页通过浏览器向本地端口发请求）。

**否掉的方案**：加登录页。单用户场景下，用户会设一个弱密码，然后每次打开都要输——这是**用真实的麻烦换取虚假的安全感**，因为本机回环接口的攻击面本来就只是本机上的恶意程序，而那种情况下密码也拦不住。

**代价**：如果哪天把服务开到局域网，当前架构是**完全裸奔**的。所以 `ARCHITECTURE.md` §7 明确写了：开放局域网必须补 token + 分权，且 `start.bat` 不提供任何 `--host 0.0.0.0` 参数，从物理上不给这个机会。

**何时重新考虑**：一旦出现"第二个人要访问"的需求，立即补 token 鉴权，不要临时改 host。

## D7 · 保留 `captures` 表存原始输入

**背景**：纯功能角度看，用户要的是"项目字段"，原文存不存不影响使用。

**选择**：每次录入都存原文 + 完整解析快照 + 用户最终采用值，只增不改。

**理由**：这个工具的核心价值是**可追溯**。三个月后看到某个项目写着"模具要改"，能点开看到是哪天、谁说的、原话是什么——这是它区别于"记在微信收藏里"的唯一理由。而且 `parsed`（机器给的）与 `apply`（人确认的）分开存，将来可以直接算解析准确率，为是否值得上 LLM 提供数据依据。

**代价**：多一张表、多一次写；原文含敏感信息，因此日志绝不能打印它（已写入 `AGENTS.md` §2.3）。

**何时重新考虑**：不需要。

---

## D8 · 前端不拆模块，保持单文件 + 两个普通 script

**背景**：55 KB 单文件，从可维护性看该拆。

**选择**：`index.html` 保持单文件承载 HTML/CSS/渲染逻辑，只把数据层抽到 `assets/store.js`、离线解析抽到 `assets/local-parse.js`，都用**普通 `<script>`**（非 module）。

**理由**：`file://` 下 `type="module"` 会因 CORS 直接失败，拆模块等于废掉离线模式。而离线模式是明天的保底方案，优先级高于代码整洁。

**代价**：`index.html` 仍然是 900 行左右的大文件；全局作用域。

**何时重新考虑**：只在"确定永远走 http 访问、不再需要 file:// 直开"之后。目前不行。

---

## D9 · 盘点向导放 P1，不进今晚范围

**背景**：用户明天要"借这个东西梳理 5～6 个项目的状态"，本质是一次性盘点，向导式（逐项目问四个问题）会顺手很多。

**选择**：今晚不做，先用现有表单（字段已齐，录入速度可接受），P1 视实际手感再定。

**理由**：明天的真实瓶颈是**用户自己还没想清楚项目状态**，不是工具不好用。向导解决的是"不知道该问什么"，而用户明确知道自己要记哪些字段（表单就是他设计的）。此时加向导属于替用户做产品决策，容易做成一个"看起来聪明但不符合他实际思路"的东西。

**代价**：明天录入可能要多点几次鼠标。

**何时重新考虑**：如果明天实际使用中出现"坐下来不知道从哪开始"的情况，说明向导价值成立，立刻做。

---

## D10 · 加一个"全量换血"的写端点，而不是逐条 CRUD

**背景**：设计和实现之间出现了一个落差。规范化的 REST 设计需要前端精确告诉后端"我改了哪个字段"，但现有前端所有写入都汇到同一个 `save()`，它手里只有整份内存数据。

**选择**：新增 `POST /api/state` 接收整份 `{customers, phases, projects}`，事务内清空重建。细粒度端点（PATCH 项目、PUT 阶段、DELETE 客户）保留给导入、脚本和测试。

**否掉的方案**：把前端 750 行里的每个 `save()` 调用点改造成定向 API 调用。技术上正确，但要改十几处写入逻辑（新增项目、编辑项目、删项目、改客户、改阶段、加里程碑…），每一处都可能漏改或改错，而**漏改的表现是"看起来保存了，刷新就没了"**——这是最糟的失败模式，而且明天之前不一定测得出来。

**代价**：
- 每次编辑写全部行（当前规模 < 200KB，实测 3ms，可忽略）
- 并发写会互相覆盖（单用户单标签页，不存在）
- 需要保证 id 在前端稳定传递（前端 `uid()` 生成的 id 会持久化，已验证）

**何时重新考虑**：项目数超过 500，或出现第二个人同时写。那时再补增量接口，`/api/state` 可保留为导入通道。

---

## D11 · 首次连上后端时不灌示例数据

**背景**：原型的 `seed()` 会造 4 个示例项目（德国 Kalom 洗碗机、法国杜邦 X200 等），让空页面看起来不像坏了。

**选择**：只有在**完全空白**（后端无项目、无客户、无阶段，且浏览器缓存也空）时才 seed。后端已自带 7 个默认阶段，因此实际首次启动是**干净的空看板**。

**理由**：明天要录的是真实项目。一进来就看见 4 个假项目，得先删掉才能开始，反而增加摩擦；而且假数据混进真实数据里容易被误当真。

**代价**：第一次打开是空的，需要知道点「＋ 新增项目」。已在空状态里写了引导文案。

**何时重新考虑**：如果空看板让人不知道从哪动手，可加一个"用示例数据看看"的次要按钮，而不是默认灌进去。

---

## D12 · 一行 = 一个型号，不是一张卡 = 一个项目

**选择**：列表视图一行一个型号，右侧抽屉放细节。

**否掉了**：把第一版的项目卡直接堆叠。九个项目 × 六条线程 = 五十多条信息摊在一屏，等于把 Excel 重造一遍。

**代价**：抽屉一次只能看一个型号，横向对比要来回点。泳道视图补偿了这一点。

**何时重新考虑**：如果实际只有三五个项目，卡片形态的信息密度反而更舒服，那时再加一个「卡片视图」开关。

---

## D13 · 线程/日志塞进 payload_json，不建表

**选择**：`projects` 只加 `model` / `order_id` / `round` 三列，其余（在办事项、日志、日期）整体存 `payload_json`。

**否掉了**：为 threads / softtasks / logs 各建一张表。前端每次保存都是全量替换，多表反而要在 `replace_state` 里做级联删除和重建，出错面更大。

**代价**：没法用 SQL 直接查"哪些线程挂了超过 7 天"。这个规模下前端算完全够用。

**何时重新考虑**：需要跨项目 SQL 统计时，或单项目线程超过两百条时。

---

## D14 · 软任务不进日历

**选择**：没有截止日的事（PI 重签、船期谈判）不排进任何一天，单独一栏按"挂了几天"排序。

**理由**：给它们编一个日期，第二天就变成假数据，而假数据比没有数据更糟——你会以为今天没到期就不急。

**代价**：日历上看不出这些事的存在。补充方式是在抽屉里显示挂起天数，超过 7 天标红。

---

## D15 · 倒推由系统算，不让人填

**选择**：填「目标发货日」，系统算生产完成日和滚动计划最晚提交日；填「已提交日」则闸门关闭。

**理由**：用户原话是"要 12 月底生产就得现在做滚动计划"。这句话应该由看板替他说，而不是靠脑子记。

**代价**：提前期默认 28 天、抽检窗口 4 天，都是估计值。项目里可以单独覆盖 `leadDays`。

---

## D16 · MD 解析放前端，不放后端

**选择**：`assets/md-import.js`，纯浏览器端，离线模式同样可用。

**理由**：切块、抽字段、算哈希都是纯文本处理，不需要服务端。少一个后端接口就少一处出错。

**代价**：将来接模型做语义抽取时，要么仍走后端 `/api/parse`，要么前端直连（不可接受，密钥会进浏览器）。

**何时重新考虑**：接入模型抽取时，把 md-import 的切块结果发给后端，只让模型处理规则抽不出的长散文段。
